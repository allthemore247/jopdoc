# Repository Guidelines

## Project Structure & Module Organization

`src/index.ts` contains the Joplin plugin entry point and DocX export workflow. Plugin metadata lives in `src/manifest.json`; keep its version aligned with `package.json`. The `api/` directory contains Joplin API declarations and supporting types generated by the Joplin plugin tooling—avoid hand-editing these files unless intentionally updating the API snapshot. `webpack.config.js` defines packaging, while `plugin.config.json` lists optional extra scripts. Builds generate `dist/`, `publish/`, and a root-level `.jpl`; these artifacts are ignored and should not be committed.

## Build, Test, and Development Commands

- `npm ci` installs the exact dependency versions from `package-lock.json`.
- `npm run dist` compiles TypeScript with Webpack, copies plugin assets, and creates the distributable `.jpl` plus metadata under `publish/`.
- `npm run prepare` runs the same distribution build and is invoked automatically during package preparation.
- `npm run updateVersion` synchronizes version information through the generator's Webpack task.

Pandoc must be installed and available on `PATH` to exercise DocX exports. For local verification, load the generated `.jpl` in Joplin and export notes containing plain text, punctuation in titles, and image resources.

## Coding Style & Naming Conventions

Use TypeScript targeting ES2015 and CommonJS, as configured in `tsconfig.json`. Follow the existing style: tabs for indentation, semicolons, single quotes for imports and most strings, `camelCase` for functions and variables, and `PascalCase` for imported types. Keep Joplin lifecycle callbacks asynchronous and await file-system operations. Prefer `path.join` over manual path construction. There is no configured formatter or linter, so keep changes focused and match surrounding code.

## Testing Guidelines

No automated test framework or coverage threshold is currently configured. Every change must at least pass `npm run dist`. Manually test the affected export path in Joplin and confirm temporary resources are cleaned up. If adding tests, place them in `testing/` and use descriptive names such as `export-images.test.ts`; add the runner command to `package.json`.

## Commit & Pull Request Guidelines

Recent history uses short, action-oriented commit subjects (for example, `added DocX functionality`). Prefer concise imperative subjects such as `handle notebook export paths`, and keep each commit scoped to one change. Pull requests should explain user-visible behavior, list build/manual test results, and link relevant issues. Include screenshots or sample exported documents when output or Joplin UI behavior changes. Do not commit generated archives, temporary files, or `node_modules/`.
